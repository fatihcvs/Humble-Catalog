## Operating envelope
Severity is judged against this envelope, never against imagined callers. Before filing any finding, the first audit enumerates every input surface - network endpoints, CLI arguments, environment, config files, data files, state files the project writes and reads back - and classifies each with one trust class, recorded in the table below. Later audits re-read the table and must not reclassify it.

Trust classes:
- adversarial: untrusted parties can reach it (public endpoints, uploads, third-party content). The full severity rubric applies, including hostile hand-crafted input.
- user-error: the project owner hand-authors it (CLI flags, config, seed data). A wrong value deserves a clear failure message; findings about exotic malformed shapes beyond that are Low at most.
- machine-generated: the project's own pipeline produces it. The generator's real output is the contract; hand-mangled or off-contract variants are out of envelope, Low at most, Declined by default.
- state-at-rest: the project writes it and reads it back. External corruption of it is out of envelope, Low at most.

Surfaces (first audit fills this in, one line each):
- CLI arguments and subcommand flags (`python -m humble_catalog ...`): user-error - the project owner types them; argparse plus the explicit `parser.error` calls in `__main__.py` are the clear-failure contract.
- Viewer HTTP API (Flask on 127.0.0.1, `humble_catalog/webapp/__init__.py`): user-error - reachable only from loopback, with the Host guard closing DNS rebinding and JSON content-type forcing a CORS preflight no cross-origin page gets past, so the callers are the viewer's own JS and the owner with curl. Not adversarial: no untrusted party can reach it.
- HumbleBundle order/bundle JSON and bundle pages (`extract.py`, `humble_api.py`, `parse_order.py`, `bundle_preview.py`): adversarial - third-party content the project does not control, reached over the network and parsed.
- External metadata API responses (`sources/*.py`, `url_import.py`): adversarial - third-party content, same reason; a compromised or merely changed upstream shape reaches the parsers.
- Cover image bytes fetched over the network (`covers.py`): adversarial - third-party bytes written to disk under a derived filename.
- Reference spreadsheets (`import-sheets`, .xlsx under `Reference spreadsheets/`): user-error - the owner hand-authors and hand-places them.
- Steam/Heroic library files on disk (`import_games.py`): machine-generated - written by those launchers; their real output is the contract.
- Environment variables (API keys, `HUMBLE_PORT`): user-error - the owner sets them.
- `catalog.db`, the harvest cache, and `covers/` read back by the project: state-at-rest - the project writes them and reads them back.
- Backup snapshots restored by `restore` (`backup.py`): state-at-rest - the project wrote them; a hand-mangled snapshot is out of envelope.

Binding rules:
- A finding exercised only by out-of-envelope input is Low at most, whatever its consequence.
- Only the user widens the envelope or reclassifies a surface. An audit that believes the envelope is wrong files one Proposed item and moves on; it never files the finding at rubric severity.
- Where robustness to malformed input on a surface is genuinely wanted, the remedy is one structural task - a single validation boundary where that input enters - never scattered per-site guards.

## Surface inventory
The audit's map, and the run's bound. Before filing any finding, the first audit enumerates the project's whole public surface - every public module, class group, entry point, or command a user can reach - as one checkbox row each, listed completely before any row is explored in depth. Enumerate from the code, not from the documentation: every source file belongs to some row, including underscore-private modules that implement public behavior, because dead or orphaned code that no entry point reaches is exactly what a call-path sweep never visits. Size rows so one checkbox certifies a comparable amount of surface: a module with dozens of public functions gets several rows split by function family, never one, or the rows-swept count overweights trivial rows and a single checkbox quietly stands for half the project. A row starts unswept: `- [ ] <surface>: <scope>`. An executed probe, and only an executed probe, flips it: `- [x] <surface>: swept at <commit> - <what the sweep exercised>`. A row whose implementing code changes after its recorded commit is stale: flip it back to unswept, because the old sweep no longer certifies the new code. A third state exists for surface this host cannot reach at all - a platform-only build, a service that cannot be installed here: `- [~] <surface>: unreachable on this host - <reason>`. It is a disclosure, not a sweep. Convergence requires no unswept `- [ ]` row, every `- [~]` row is named with its reason in the run report, and a later run on a host where the reason no longer holds flips it back to `- [ ]` and sweeps it.

For a surface that computes values, a probe is a correctness check, not a liveness check. Sweeping such a row requires at least one known-answer test per function family it covers - a closed form, a hand-computed small case, or an independent reference implementation - or a strong invariant that a wrong result would break. Run-without-crashing flips nothing there: the costliest defects return wrong numbers without complaint, and a crash-biased sweep files every type error while certifying wrong arithmetic as clean. A metric off by a constant factor, a parameter silently ignored, and an aggregation that quietly no-ops all pass a liveness probe and all fail a known-answer one. A row's known-answer battery is kept, not rebuilt: write it under `.jeffy/probes/<row-slug>` so the iteration checkpoints commit it, and a re-sweep re-runs that battery instead of reconstructing the instrument, which is where most re-sweep cost goes. A battery is updated in the same iteration as the behavior it pins, so it never certifies a contract the code no longer has.

A sweep also exercises every documented parameter of the functions it certifies, at two or more values that must change the output, including the negative or boundary side of the domain where one exists. A documented parameter whose value changes nothing is a finding, never a pass, unless the documentation itself says it should have no effect in that case. This is a recurring class, not a corner: an inert flag, a rate applied only when positive, and an aggregation token falling through to no-op are the same defect wearing three names, and a sweep that probes a parameter only where it works will certify the row while the parameter is dead everywhere else.

Dimension scores claim only swept rows. A None on a dimension whose surface still has unswept rows is silence, not cleanliness, and an audit that presents such a score as the whole project is the failure this table exists to prevent: a library scored correctness None across five audits while an entire simulation module sat unexamined, and every audit's new High was simply the next unvisited room. The first audit therefore probes breadth-first - every row shallowly before any row deeply - so the worst defect in the project appears in the first filing, not the sixth.

Convergence requires that this table lists no unswept row, and the Stop hook checks that mechanically. That is what makes the loop bounded: the surface is finite, sweeps only accumulate, and the remaining work is always the visible remainder of a written list rather than a hope that the next audit comes back empty. The run report states progress as rows swept of rows total.

## Verify command
One runnable command that must exit 0 for this project to count as unbroken - the test suite, the build, or a validator script. The first audit fills this in; write none with a one-line reason only if the project genuinely has no runnable gate. It runs at the end of every iteration: a failure the previous checkpoint did not have means the iteration broke the project, and the iteration is reverted.

Command: `.venv/Scripts/python.exe -m pytest -q && .venv/Scripts/python.exe scripts/check_no_data_tracked.py && .venv/Scripts/python.exe scripts/leak_check.py`

That is exactly what `scripts/windows/verify.ps1` runs, spelled so bash can execute it on this host: the project's test suite, then the two privacy gates the owner's standing order requires. It is written as the three steps rather than as a call to the .ps1 wrapper because the wrapper needs PowerShell and reports failure through `Write-Error`, whose exit status depends on `$ErrorActionPreference`; `&&` between the three makes the failure status unambiguous. Takes roughly 90 seconds.

## Method
Audit the project against every applicable dimension and score each by its highest finding severity: High, Medium, Low, or None. Skip dimensions that do not apply and record why. Every audit consults the Surface inventory first and sweeps unswept or stale rows before re-probing swept ones; an audit never wanders. When replenishing with a partial audit, target the dimensions least recently scored and the inventory rows least recently swept.

Severity rubric - judge by consequence, not by effort to fix:
- High: users get wrong results, data loss or corruption, a security vulnerability, a crash on realistic in-envelope input, or a broken build or install.
- Medium: failure on a plausible in-envelope edge case, a silently swallowed error, missing tests on a path whose failure would matter, misleading documentation, or a dependency with a known vulnerability.
- Low: polish - naming, style, minor docs, cosmetic gaps.

Evidence rule: a finding exists only if you can point at it - a file and line, a failing command, or a reproduced behavior. Verify before filing; no speculative findings. File the root cause, not each symptom.

Publication rule: code that leaves this project - an issue body, a pull request description, a report, a message to anyone - must be run in exactly the form it is published, and its stated output must be that run's real output. Trimming a working script down to something shorter and clearer does not inherit the original's verification: a reduction is new code, and it is unverified until it has been executed as written. Verifying one artifact and shipping a different one is the failure this rule exists to stop, and it is expensive, because the person who finds the broken version is the person whose trust was being asked for.

Write findings into BACKLOG.md as prioritized checkable tasks, worst severity first: High in Now, Medium in Next, Low in Later; break ties by user impact, then by smallest effort. Each line names its class: `- [ ] <ID> (<Severity>, <class>, <dimension>): <finding>. Acceptance: <check>.` - class is one of runtime, test, build-ci, docs, dev-tooling, chosen by the files the fix will touch, and a legacy line without one is read as runtime. Order within a section by severity first, then runtime before the other classes, because shipped behavior is what a user meets and perimeter work is what a run drifts into. Every task must be completable in a single iteration - split it if not - and must carry an acceptance check that is a runnable command or an observable fact, never an opinion. An acceptance check must be strong enough to fail: run it against the unfixed code and confirm that it does, because a check the broken implementation also satisfies proves nothing. Prefer a differential or invariant assertion over an absence-of-badness one - a sweep asserting only that output holds no NaN and no infinity is satisfied by a function that returns a constant, and a green suite, full line coverage and that sweep all passed at once over exactly that defect. For a user-facing surface, the check must exercise the running surface end to end - drive the UI (browser automation where available) or invoke the real CLI; a unit test alone does not close a user-facing task. A finding judged not worth fixing goes under Declined with a one-line reason; never re-file a Declined item. Not worth fixing is priced, not felt: a Low whose class is not runtime and whose fix plus its regression test cannot be completed inside one iteration is by policy not worth fixing, so move it to Declined with the reason `cost: exceeds one iteration` and name it by ID in the run report; that pricing outranks the splitting rule above, because splitting such a Low into two one-iteration tasks is exactly how the price gets evaded. That is a Declined reason and never a severity change; severity is set by the rubric and the envelope alone, and downgrading a finding to reach convergence is a violation.

Class rules: when a finding is one instance of a repeatable idiom - a type guard, a parse, an escape, an error path - file and fix the class, not the instance. The fix's acceptance check must include an enumeration, a grep or AST listing of every site where the idiom appears, and every site must be covered or explicitly settled. Record each closed or declined class as one line under Settled classes in BACKLOG.md. Three-strike rule: the third finding sharing one root cause with two earlier findings ends instance work; replace it with either one structural task that closes the class at a boundary or one Proposed envelope decision, and never patch a fourth instance.

Working rules, each of them learned by losing an iteration to it: an inventory row's scope line names the enumeration command that defines it - the grep, the listing, the glob - never prose, because a scope nobody can re-run is a scope nobody can check; a removal task greps the docs for the removed names in the same iteration; a fix iteration runs the filed reproduction as its first command, because backlog lines are hypotheses that rot as sibling fixes land around them; and a hash written into a state file is copied from rev-parse output, never typed.

Closeout: a run that has produced one full fresh-evidence audit scoring zero High and zero Medium in-envelope stops auditing for the rest of the run, works or declines whatever is already on the ledger, and converges. Without that stop a project with a long tail of Low findings never finishes: the ledger drains, the drain triggers a replenishing audit, the audit files another Low, and the loop is productive forever without ever being done. The stop is safe because reaching it requires an audit that just came back clean of High and Medium; a High or Medium found while executing a task is still filed and still worked, and both the evaluator gate and the next run's fresh audit remain in force.

Audit discipline: the audit procedure is exactly what this Method prescribes. Never escalate rigor unilaterally - no improvised sub-auditor panels, no fuzzing campaigns, no dimensions beyond the Goal's list; the single convergence evaluator defined in the Definition of done is the only sub-agent review this Method authorizes. A case for more rigor is a Proposed item naming its cost; the user decides. Never file a finding inside a class recorded under Settled classes unless the code implementing that class changed after settlement. A finding a previous full audit scored clean, on code unchanged since, needs new evidence - a reproduced failure - not a deeper reading of the same lines.

## Constraints
- Do not change public interfaces or observable behavior without recording the rationale in JOURNAL.md.
- Do not weaken security, weaken or delete tests, or remove features to make a metric pass.
- Full implementations only. A placeholder or stub written to satisfy an acceptance check is a violation, not progress.
- A task is done only when its acceptance check has been run and observed to pass. Evidence over assertion, always.
- Prefer deletion and simplification over addition. No speculative abstractions, options, or features.
- Match the project's existing conventions. No wholesale reformatting or cosmetic churn.
- Prefer well-maintained, widely adopted libraries. No heavy dependencies for trivial problems.
- Keep each change atomic. The per-iteration checkpoint commit is the revert unit; never push, never create branches, and never rewrite checkpoint history.

## Lessons
Operational rules future iterations must obey, learned during runs. One line each: a build quirk, a command that must or must not be used, a mistake made twice. When a JOURNAL Learnings line states a rule future iterations need, copy it here as one line. The project owner can add lines here too, to steer every future run: fix the loop, not the run. Keep it brief; never write status reports, run narration, or task state here. A Lesson recording its second occurrence is marked `[recurred]`, and the run report proposes promoting it to a mechanism - a hook check or a Method rule - for the user to decide: a rule that had to be written twice is a rule this text is not enforcing.

- Read the `CREATE TABLE` before writing a probe that inserts rows; guessing columns costs a run, and on Windows the failed connection holds the temp file open so the real error is buried under a tempdir PermissionError.
- Sweep a retry or backoff policy by counting attempts and sleeps, never by watching a call succeed: "it worked" looks identical whether the policy retried three times, once, or not at all.
- The privacy standing order in CLAUDE.md outranks everything here: probes, fixtures, docs and commit messages use invented titles from docs/TEST-DATA.md, never real library items. `leak_check.py` is part of the Verify command, so a breach fails the gate.
- `[recurred]` The leak gate can block vocabulary you cannot reword - a standard library class name tripped it once, and a builtin exception class name tripped it again, in prose merely naming the error a defect would raise. Name such an error by what it means rather than by its identifier; do NOT widen ALLOWED, which would blind the gate to real titles.
- `[recurred]` Prefer plain technical wording in probe and state files: any evocative English noun may collide with a private-library term through the substring matcher. Tripped 5 times on prose alone, never on a real leak. Ordinary technical vocabulary is not safe either - two common words in one backlog entry collided, one of them the name of a builtin exception class - so run the gate before the checkpoint rather than at the end of the iteration.
- A probe's fixture must not read a constant the unfixed code lacks: the helper raises, the case passes for the wrong reason, and the differential run silently measures nothing. Hold such a value as a literal and assert it equals the shipped constant separately.
- A class is enumerated by listing every site of the IDIOM, never by grepping for the fix: a grep that matches only already-fixed sites is structurally blind to the unfixed ones and will certify an incomplete class as settled.
- Genre names are private data too, not neutral vocabulary: a plausible one used as a probe fixture tripped the gate in iteration 3. Invent an obviously fake one rather than widening `ALLOWED`.
- Probe a network guard with real `http.server` instances on ephemeral ports, never a mocked session: a mock proves only what it was written to do.
- Never branch on `requests`' `is_redirect` (or any truthiness) in code the suite drives with `Mock` responses - every Mock attribute is truthy. Compare `status_code` against an explicit set.
- A battery asserts the DESIRED answer, never the observed one. A case written to match current behaviour certifies a defect as correct forever.
- A probe that opens a database uses a FRESH file per case. Reusing one carries the previous case's rows into the next and trips the `machine_name` UNIQUE constraint.
- `bool` is a subclass of `int` in Python: a range check on a JSON number must exclude it explicitly, or `true` passes as 1.
- Never pipe a test run or the Verify command through `Select-Object -Last N` in PowerShell: like `head`/`tail` in bash it reports the pipeline's status, not the suite's, so a red suite reads as green. Redirect to a file and check the exit status.
- The `[~]` inventory marker means unreachable on this host and nothing else. A row that is only partly swept splits into two rows; it never gets `[~]`.
- `.venv/Scripts/pip.exe` exits 1 silently in this project; use `.venv/Scripts/python.exe -m pip` instead.
- `[recurred]` A differential run needs the fix reverted and NOTHING else. Reverting a module that also gained a new name - an accessor, an exception class - breaks the import, and pytest reports a collection error, which looks like a red run and measures nothing. When the fix introduces a name the new tests import, the differential belongs in a probe battery that does not name it; run that battery before editing and record its score.
- Assert a close DIRECTLY - the connection object must raise on reuse - never "a second open still works". The weaker form only fails when a write was still pending, so on any path holding no lock it passes against the very defect it was written for.
- A round-trip invariant over a value that was rounded needs a tolerance of half the rounding step, or it fails on correct code: 4667 parsed to two places gives 4.67, and multiplying back gives 4670, not 4667.
- A probe of a keyed source clears that provider's API-key environment variable before importing it. Every keyed source falls back to `os.environ` when no key is passed, so on a host where the owner has exported a real key the "source is unconfigured" cases send a real request and assert the opposite of what they claim; this passed spuriously once before the variables were cleared.
- `leak_check.py` matches SUBSTRINGS, so ordinary English prose in PLAN.md, BACKLOG.md or JOURNAL.md can trip it with no private data present. The Jeffy template's own Definition-of-done wording tripped it on one ordinary noun in iteration 1. Reword the prose; do not add a generic word to `ALLOWED`, which would blunt the gate for the whole repo. Do not quote the offending word in the Lesson either - that just moves the hit.

## Definition of done
Convergence requires a full audit pass, executed in one iteration, that rescores every applicable dimension against the severity rubric and the Operating envelope with fresh evidence and finds zero High and zero Medium in-envelope findings, requires that the Surface inventory lists no unswept row - a converged project is one whose whole mapped surface has actually been examined, enforced mechanically by the Stop hook - and it leaves no open task behind: at convergence the Now, Next, and Later sections of BACKLOG.md are empty, because every filed finding, Low included, has been completed, moved to Declined with a genuine not-worth-fixing reason, or blocked with its reason recorded and named in the run report. A converged project is completely done, not done except the small things. A `- [~]` row - surface this host cannot reach, carrying its reason - is not an unswept row and does not block convergence, but the run report names every one of them. When the closing audit itself files new findings the run is not yet converged: execute them in the following iterations and declare convergence once the backlog is empty again, provided the only commits since that clean audit are the fixes for tasks it or the evaluator gate filed plus loop state edits and the Verify command exits 0 in the declaring iteration with its output recorded in the JOURNAL entry; if anything else changed, audit again. Proposed items never block convergence. Partial or replenishment audits never count toward convergence. Convergence also requires the adversarial evaluator gate: exactly one fresh-context sub-agent, spawned carrying none of the run's context, re-runs the Verify command and the closed tasks' acceptance checks, hunts for missed in-envelope High or Medium findings in the run's changes, and must return PASS, recorded in the JOURNAL entry of the iteration that ran it; a PASS that does not declare in the same iteration does not carry forward, and the declaring iteration re-invokes the gate so its closing entry records the verdict the Stop hook reads there; a REJECT files its evidenced reasons as ordinary tasks and the run continues, at most 2 evaluator invocations per run and 3 when the first landed before the midpoint of the budget, a second REJECT ends the run as a hard blocker, a cap reached without a PASS in the closing entry ends the run the same way because no invocation remains to produce the verdict declaring requires, and when sub-agent spawning is unavailable the run records Evaluator: unavailable with the reason and may converge under the remaining conditions. The gate is not only a closing ceremony: when the ledger first empties with a clean full audit already recorded this run and at least 3 iterations remaining, run it that iteration rather than at the declaration, because a REJECT files tasks and answering them needs budget the last iteration no longer has. The ratchet never invokes the evaluator. Severity is set by the rubric and the envelope alone: downgrading a finding to reach convergence is a violation, and Declined items must be genuinely not worth fixing, not deferred work. Pricing is how not worth fixing is judged: a Low whose class is not runtime and whose fix plus its regression test does not fit in one iteration goes to Declined with the reason `cost: exceeds one iteration`, named by ID in the run report - a Declined reason, never a lower severity. Every run ends with a run report to the user - converged, out of budget, or blocked - listing iterations used, tasks closed with severities, the run's diffstat, blocked and Proposed items, and the final Verify status. Record the closing scores and their evidence in JOURNAL.md, and, when the project is a git repository, append a line reading Converged: <full commit hash> - <date> under the ## Converged section of BACKLOG.md, before claiming convergence.

Convergence ratchet: when the latest Converged line in BACKLOG.md names a commit, no open task remains in Now, Next, or Later, the run carries no focus directive, and nothing but loop state has changed since that commit - every path in git status --porcelain and in git diff --name-only against that hash is one of PLAN.md, BACKLOG.md, JOURNAL.md, JOURNAL-archive.md, or a path under `.jeffy/`, which holds the probe batteries and is loop memory exactly as the ledger files are - verify exactly that and re-declare convergence immediately, without a fresh audit. A seeded backlog or a focus directive always gets a real audit or execution, never a ratchet. When code has changed, audit normally, but a finding in code unchanged since the convergence commit must be a reproduced in-envelope High or a regression traced to the new changes; anything else there is a Proposed item. In a project without git the ratchet degrades to the Settled classes rule alone. The iteration budget is the hard stop.
